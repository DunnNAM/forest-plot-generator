# Context: RShiny Dashboard Code Review

## Project Architecture
* **Architectural Pattern:** This application does **not** follow a strict Shiny module pattern (`moduleServer` / `NS()`). Instead, it adopts a **function-based, file-split architecture** (DEC-004):
  * **UI Composition (`ui.R` & `R/ui_*.R`):** UI sections are organized into functional builder/helper functions within `R/` (auto-sourced by Shiny, e.g. `R/ui_plot_options.R`, `R/ui_drawers.R`, `R/ui_rail.R`) and assembled in `ui.R`.
  * **Server Decomposition (`server.R` & `server/*.R`):** `server.R` is a lightweight coordinator that sources domain-specific server scripts from `server/` (e.g. `upload.R`, `regression.R`, `preview.R`, `plot.R`, `export.R`, `drawers.R`, `observers.R`, `wizard.R`) using `source(..., local = TRUE)`.
  * **Pure Logic & Helpers (`R/helpers.R`):** Non-reactive utility, formatting, and data transformation functions are extracted as pure functions in `R/helpers.R` for direct unit testing.
  * **Core Files:** `global.R` (dependencies, font loading, data setup), `ui.R`, and `server.R`.
  * **Testing Suite:** Pure helper unit tests in `tests/testthat/test-helpers.R`; application integration tests in `tests/testthat/test-shiny-app.R`.

## Analysis Rules & Guidelines
1. **Scope & ID Management (No `ns()`):** Do not enforce or expect Shiny module namespaces (`ns()`). Since the app shares a single top-level namespace, verify that input and output IDs are unique, consistent, and correctly matched between functional UI builders (`R/`, `ui.R`) and server files (`server/`).
2. **Server Environment & Scoping:** Server files are sourced with `local = TRUE` inside the `server` function closure, sharing `input`, `output`, `session`, and reactive objects. Ensure state is cleanly passed or tracked via shared reactives/sessions within this environment closure rather than mutating the global environment (`<<-`).
3. **Reactivity Performance:** Identify duplicate reactive evaluations and unnecessary dependency invalidations. Flag heavy data operations, plot generation routines, or regression fits that lack appropriate `shiny::isolate()` wrappers or debounce guards.
4. **Package Namespace Qualification:** Ensure all external package function calls explicitly declare their package namespace (e.g., `shiny::runApp()`, `dplyr::mutate()`, `bslib::page_navbar()`, not bare function calls), unless an explicit convention or exception is justified.
5. **Function Separation & Testability:** Verify that non-reactive computations and business logic reside in testable helper functions in `R/` rather than being deeply embedded in reactive observers or UI declarations.
6. **Architecture & Wiring:** Ensure the functional split adheres to established project conventions (DEC-004), maintaining clean boundaries between UI builders, server reactive pipelines, and pure utilities for ease of maintenance.
